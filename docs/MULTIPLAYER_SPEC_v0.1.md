# FOOTBALL LEAGUE マルチプレイ仕様 v0.1

## 0. この仕様書の扱い

本仕様は、現行シングルプレイ版を壊さずにマルチプレイ版を作るための初期設計である。

現行完成版は `stable/single-player-v1` に退避済みとし、マルチプレイ開発は `dev/multiplayer-v1` で行う。

この仕様書の内容を一括実装してはいけない。各Stageごとに実装、確認、必要最小限の修正を行う。

## 1. 基本方針

マルチプレイは、リアルタイム操作型ではなく、非同期ターン制として扱う。

各プレイヤーは自分のクラブの編成や戦術を決定し、全員の入力が揃った後にサーバー側でシーズンを一括シミュレーションする。

試合中のプレー単位の通信は行わない。

## 2. 最初に目指す範囲

Stage M1 では、以下を目標にする。

- ルーム作成
- ルーム参加
- クラブ選択
- 編成保存
- 戦術保存
- 準備完了
- 全員準備完了後、ホストがシーズンを一括実行
- 結果共有

## 3. 後回しにする範囲

初期マルチプレイでは、以下は実装しない。

- ドラフトのマルチ対応
- オークションのマルチ対応
- 契約更新のマルチ対応
- 育成、覚醒、特別特訓のマルチ対応
- 放出フェーズのマルチ対応
- 詳細な試合イベントログ共有
- チャット
- 観戦
- ログイン認証

## 4. Cloudflare構成

想定構成は以下とする。

- Cloudflare Pages: フロントエンド配信
- Cloudflare Workers: API入口
- Durable Objects: ルームごとの状態管理
- D1: 長期保存が必要になった段階で追加

初期実装では、D1は必須にしない。

## 5. Durable Objectの役割

1つのルームを1つのDurable Objectで管理する。

Durable Objectは以下を保持する。

- roomId
- hostId
- phase
- league状態
- 参加プレイヤー一覧
- 各プレイヤーの担当クラブ
- 各クラブの編成
- 各クラブの戦術
- 各プレイヤーの準備完了状態
- シーズン結果

## 6. ルームフェーズ

初期フェーズは以下とする。

```txt
LOBBY
CLUB_SELECT
LINEUP
READY
SIMULATED
RESULTS
```

### LOBBY

ルーム作成直後。参加者を待つ。

### CLUB_SELECT

参加者が操作クラブを選ぶ。

### LINEUP

各プレイヤーが編成と戦術を決める。

### READY

全プレイヤーが準備完了した状態。ホストがシーズン実行できる。

### SIMULATED

サーバー側でシーズン一括処理済み。

### RESULTS

全員が結果を閲覧できる状態。

## 7. 通信方針

試合中の逐次通信は行わない。

送信するのは、主に以下とする。

```txt
プレイヤー → サーバー
- playerName
- clubId
- lineup
- tactic
- ready

サーバー → プレイヤー
- room状態
- 参加者状態
- 担当クラブ
- シーズン結果
```

## 8. 試合結果データ方針

初期マルチプレイでは、イベントログは共有しない。

共有する結果は以下を基本とする。

- 最終順位表
- 各クラブの勝敗
- 得点
- 失点
- 勝点
- 人間クラブの10試合スコア
- 個人成績
- MVP
- Best5

CPU同士の詳細ログは保存しない。

## 9. 現行シミュレーションとの関係

試合計算・リーグ計算は、できる限り現行の `league.js` / `sim.js` を使う。

ただし、ブラウザ依存処理、DOM操作、localStorage依存処理はWorker側に持ち込まない。

サーバー側で使う計算ロジックは、純粋な関数として切り出す方針とする。

## 10. 保存方針

初期段階では、Durable Object内の状態保存を優先する。

D1は以下が必要になった段階で追加する。

- ルームを閉じた後も履歴を残したい
- 10シーズンの記録を長期保存したい
- 過去リーグを一覧表示したい
- 複数端末から継続プレイしたい

## 11. ホスト権限

初期実装では、ルーム作成者をホストとする。

ホストだけが以下を実行できる。

- フェーズ進行
- シーズン一括実行

全員が準備完了していない場合、ホストはシーズン実行できない。

## 12. 放置対策

初期実装では自動進行は行わない。

後続Stageで以下を検討する。

- ホストによるCPU委任
- 一定時間経過後の自動CPU操作
- 未入力プレイヤーの離脱扱い

## 13. Stage分割

### M1: 設計と土台

- マルチ仕様書追加
- Cloudflare構成方針整理
- 既存シングル版の保護

### M2: ルームAPI土台

- Workerエントリ追加
- Durable Objectクラス追加
- ルーム作成API
- ルーム取得API

### M3: 参加とクラブ選択

- 参加API
- プレイヤー名登録
- クラブ選択API
- CPUクラブとの共存

### M4: 編成・戦術送信

- lineup送信
- tactic送信
- ready送信
- 全員準備完了判定

### M5: サーバー側シーズン一括実行

- サーバー側でリーグ計算
- 結果JSON生成
- 結果共有

### M6以降

- ドラフト
- オークション
- 育成
- 契約
- D1保存
- WebSocket同期

## 14. 注意事項

- `main` を直接壊さない。
- `stable/single-player-v1` を現行完成版として扱う。
- `dev/multiplayer-v1` でのみマルチプレイ作業を進める。
- 現行シングルプレイの進行を前提なく書き換えない。
- イベントログ共有は初期範囲外とする。
